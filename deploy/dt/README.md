## Deployment boundary

`https://app2.thatcampus.com` is the isolated Digital Twin web and API origin. The `thatcampus-dt-edge` Cloudflare Worker accepts only that public host and forwards its method, path, query, authentication and request body to the reviewed `thatcampus-dt` Cloud Run service in `eduera-511111`, region `asia-south1`. It does not route the ERP or marketing hosts. The backend retains cookie/CSRF and native Bearer authority; the edge does not authenticate users or replace owning API checks. Edge transport failures return a safe JSON 503 with different read versus unconfirmed-action copy, without replaying requests.

The single image contains the compiled backend, the sole `mobile/` Expo web export, production dependencies, required brand/font assets and PostgreSQL 17 `pg_dump`. Retained `frontend/src` is an input to the unchanged Simulation source audit in the build stage only. No old frontend package, build or runtime enters the final image. Build-source upload filtering and the Dockerfile-specific allowlist exclude `.env`, credentials, local dependencies, private dumps, runtime state and verification artifacts before their respective upload/build boundaries. Use BuildKit; an image cache is not a substitute for the strict source gate.

Runtime is the non-root `node` user, UID/GID 1000, working directory `/app/backend`, command `node dist/main.js`, listening on `0.0.0.0:8080`. `SPA_DIST_DIR=/app/web-dist`; uploads use `/app/storage/leave-documents`; `SIMULATION_PG_DUMP_PATH=/usr/lib/postgresql/17/bin/pg_dump`. Production builds explicitly set `EXPO_PUBLIC_API_URL=https://app2.thatcampus.com` and disable dotenv loading. Browser API calls remain same-origin. The backend serves Expo entry/chunk assets, fonts and the exact local CanvasKit WASM, including its license, with the reviewed CSP. Ordinary JavaScript `unsafe-eval` is not enabled.

## Failure and rollback

Before promotion, a failed build, binding check, smoke or migration leaves the previous production traffic assignment in place. Stop and inspect the exact build/job/revision receipt; there is no general mutation retry wrapper. After promotion, a failed public smoke requires an operator decision: the script does not silently move traffic back.

Code rollback means directing the **new DT service only** to a retained, known-good DT revision/digest. First check that the older code can read the current schema and persisted data. If compatible, an operator may run the following after substituting the reviewed DT revision, then verify the public origin and retain the outcome:

```sh
gcloud run services update-traffic thatcampus-dt \
  --project eduera-511111 --region asia-south1 \
  --to-revisions '<reviewed-DT-revision>=100'
```

Traffic rollback does not undo a migration, restore a database, revert files or reverse accepted domain actions. Prefer repair forward when compatibility is uncertain. Any database restore requires its own exact-target review, backup/recovery plan, stopped/quiesced writers and explicit authorization; never restore over the old ERP or normal development databases. Do not repeat an uncertain migration or initial import to simulate rollback.
